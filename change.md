This repository's Drips Wave application was rejected, so this change set focuses on demonstrable Soroban development rather than presentation. The codebase was already Stellar-only, with no EVM dependency and a Soroban receipt contract, so the correction was not a chain migration from scratch but a completion of the Soroban design: the contract now owns the facts that the application previously inferred or trusted, and the application now reads those facts back from the chain instead of relying on browser state or caller-supplied metadata.

The contract in `contracts/stellarproof` was extended to v0.2. `Receipt` now stores `token: Address`, the Stellar Asset Contract that actually moved the funds, so a verifier can prove which asset was paid even though `token_symbol` remains a payer-reported display label. The `ReceiptAnchored` event carries the token address as well. A bounded `get_receipts_by_user_page(user, start, limit)` function was added, with the page size clamped to 50 so a read cannot exhaust the invocation budget. A permissionless `bump_receipt(receipt_id)` function was added; it extends the receipt and both user indexes to the full persistent TTL and emits `ReceiptRenewed`, with no admin, no authorization, and no custody introduced. Existing functions, error codes, and the atomic transfer-then-write behavior are unchanged.

On the server, `readReceiptOnchain` now returns the stored token address and derives an approximate expiry from the ledger entry's `liveUntilLedgerSeq`, so TTL is read without a contract-side getter (the host does not expose one to production contract code). Two routes were added: `GET /api/stellar/receipts` reads one page of an account's onchain history by simulating `get_receipts_by_user_page` and then reading each id from persistent storage, and `POST /api/stellar/renew-receipt` builds and simulates the `bump_receipt` envelope for the connected account to sign. Submission still goes through the existing `/api/stellar/submit-payment` route, so there is one signing and submission path rather than a second transaction pipeline.

On the client, `OnchainReceipt` and `ReceiptData` gained optional token and expiry fields. The dashboard now merges the account's onchain history with the local cache when a wallet is connected, treating onchain values as authoritative while keeping AI metadata and transaction hashes from the local copy; a new device therefore sees the same receipts, not an empty browser store. The receipt detail and public verifier display the token contract with an explorer link, label the symbol as payer-reported, show the storage expiry, and the receipt detail adds an "Extend record" action that signs and submits a renewal. README and the in-app `/docs` page were updated to document the new functions, routes, storage layout, and the revised verification limits.

Testing and documentation were updated accordingly: the Rust suite now has 15 tests covering token storage, paging boundaries, permissionless renewal, event topics, missing authorization, duplicate ids, self-payments, and the original validation errors; the TypeScript suite has 26 tests including the new routes' validation and unconfigured-contract behavior. The maintainer issue batch in `scripts/create-issues.sh` was trimmed of the items this change completes and now defines Drips Wave complexity labels. `cargo test`, `cargo fmt --check`, `cargo clippy --workspace --all-targets`, `npm test`, `npm run lint`, `npm run typecheck`, and `npm run build` all pass. After the checks passed, v0.2 was deployed to Stellar Testnet as `CD7JEZD2N3T25ROZ2YTG3DYMO65NWWGXSD5ZSCRIZ36PUSWVVA34JAY5` from a fresh Friendbot-funded deployer, and `NEXT_PUBLIC_STELLARPROOF_CONTRACT_ID` now points at it. The deployed contract was smoke-tested onchain: `get_receipts_by_user_page` returned an empty page for a new account, and `bump_receipt` on a missing id failed with `ReceiptNotFound` (error 5). Because v0.2 is a new contract ID, v0.1 receipts are not migrated and old entries have an empty token field. The project remains Testnet-only and unaudited.

## v0.3: asset-derived symbols and recipient acknowledgement

The v0.2 receipt still trusted the payer for the asset label and could not record any counterparty agreement. v0.3 closes both gaps without adding an admin key, an upgrade path or custody.

The contract now resolves `token_symbol` itself. `create_receipt` calls SEP-41 `symbol()` on the token contract through `Env::try_invoke_contract`; the stored symbol is therefore the asset's own metadata, and the caller-supplied string survives only as a fallback for tokens that do not implement the interface. The native Stellar Asset Contract reports `native`, which the server maps to `XLM` for display; storage and events keep the raw SAC value.

Recipient acknowledgement is additive. `acknowledge_receipt(receiver, receipt_id)` requires the recorded receiver's signature, rejects any other address with `NotReceiver` (6), rejects a second call with `AlreadyAcknowledged` (7), stores the ledger timestamp under `DataKey::Acknowledgement(receipt_id)`, and emits `ReceiptAcknowledged`. `get_acknowledgement` returns the timestamp or `None`. The `Receipt` struct and existing storage encodings are unchanged, so a receipt remains payer-attested and an acknowledgement is a separate, distinguishable attestation. `bump_receipt` now extends the acknowledgement entry alongside the receipt and its indexes.

On the server, `readReceiptOnchain` fetches the receipt and acknowledgement ledger entries in one `getLedgerEntries` call, so public verification stays stateless, and returns `acknowledgedAt`. A new `POST /api/stellar/acknowledge-receipt` route builds and simulates the receiver's envelope; submission still goes through the existing `/api/stellar/submit-payment` route. The receipt detail shows acknowledgement state and offers the action only to the connected recipient, the public verifier shows the acknowledgement or states that none exists, and the dashboard merges the new field from the onchain record.

Testing: the Rust suite has 23 tests, adding mock-token symbol resolution, the no-SEP-41 fallback, acknowledgement success, wrong receiver, duplicate, missing receipt, missing auth, event topics and renewal retention. The TypeScript suite has 29 tests, adding the acknowledgement route's validation and unconfigured-contract behavior. `cargo test`, `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets`, `pnpm typecheck`, `pnpm lint`, `pnpm test` and `pnpm build` pass, and `stellar contract build` produces 8 exported functions.

The deployed contract was smoke-tested with a real 0.005 XLM payment: storage recorded the token address and the SAC's own symbol, the receipt and acknowledgement were read back with `getLedgerEntries`, the recipient's acknowledgement transaction succeeded, and the receiver's paged history returned the new receipt id. v0.3 is a new contract ID, so v0.1 and v0.2 receipts are not migrated. The project remains Testnet-only and unaudited.
