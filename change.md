This repository's Drips Wave application was rejected, so this change set focuses on demonstrable Soroban development rather than presentation. The codebase was already Stellar-only, with no EVM dependency and a Soroban receipt contract, so the correction was not a chain migration from scratch but a completion of the Soroban design: the contract now owns the facts that the application previously inferred or trusted, and the application now reads those facts back from the chain instead of relying on browser state or caller-supplied metadata.

The contract in `contracts/stellarproof` was extended to v0.2. `Receipt` now stores `token: Address`, the Stellar Asset Contract that actually moved the funds, so a verifier can prove which asset was paid even though `token_symbol` remains a payer-reported display label. The `ReceiptAnchored` event carries the token address as well. A bounded `get_receipts_by_user_page(user, start, limit)` function was added, with the page size clamped to 50 so a read cannot exhaust the invocation budget. A permissionless `bump_receipt(receipt_id)` function was added; it extends the receipt and both user indexes to the full persistent TTL and emits `ReceiptRenewed`, with no admin, no authorization, and no custody introduced. Existing functions, error codes, and the atomic transfer-then-write behavior are unchanged.

On the server, `readReceiptOnchain` now returns the stored token address and derives an approximate expiry from the ledger entry's `liveUntilLedgerSeq`, so TTL is read without a contract-side getter (the host does not expose one to production contract code). Two routes were added: `GET /api/stellar/receipts` reads one page of an account's onchain history by simulating `get_receipts_by_user_page` and then reading each id from persistent storage, and `POST /api/stellar/renew-receipt` builds and simulates the `bump_receipt` envelope for the connected account to sign. Submission still goes through the existing `/api/stellar/submit-payment` route, so there is one signing and submission path rather than a second transaction pipeline.

On the client, `OnchainReceipt` and `ReceiptData` gained optional token and expiry fields. The dashboard now merges the account's onchain history with the local cache when a wallet is connected, treating onchain values as authoritative while keeping AI metadata and transaction hashes from the local copy; a new device therefore sees the same receipts, not an empty browser store. The receipt detail and public verifier display the token contract with an explorer link, label the symbol as payer-reported, show the storage expiry, and the receipt detail adds an "Extend record" action that signs and submits a renewal. README and the in-app `/docs` page were updated to document the new functions, routes, storage layout, and the revised verification limits.

Testing and documentation were updated accordingly: the Rust suite now has 15 tests covering token storage, paging boundaries, permissionless renewal, event topics, missing authorization, duplicate ids, self-payments, and the original validation errors; the TypeScript suite has 26 tests including the new routes' validation and unconfigured-contract behavior. The maintainer issue batch in `scripts/create-issues.sh` was trimmed of the items this change completes and now defines Drips Wave complexity labels. `cargo test`, `cargo fmt --check`, `cargo clippy --workspace --all-targets`, `npm test`, `npm run lint`, `npm run typecheck`, and `npm run build` all pass. One honest limitation remains: v0.2 deploys as a new contract ID, and this change set does not deploy it, because that requires a funded Testnet deployer secret. The documented Testnet ID still points at v0.1 until a maintainer runs `pnpm deploy:testnet` and updates `NEXT_PUBLIC_STELLARPROOF_CONTRACT_ID`; v0.1 receipts are not migrated, and old entries have an empty token field. The project remains Testnet-only and unaudited.
